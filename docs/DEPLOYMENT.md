# Deployment and recovery

## Combined Render release

The root `Dockerfile` builds the existing React frontend and Fastify backend, generates Prisma Client, installs Python/pypdf, and runs one non-root Node process. `/` redirects to `/app/`; `/app/*` serves only compiled public assets and extensionless SPA routes. Source maps and dotfiles are denied. APIs retain Clerk authorization. The legacy source is preserved in Git and is not served as the homepage. No migrations or seeds run at startup. The production image excludes development dependencies.

`render.yaml` selects a **free** single-instance Docker web service, manual deploys, and `/api/ready`. Never enable a paid plan without owner approval. Render free instances can sleep and cold-start; the public demo is not an availability guarantee. The Docker build is additionally checked by GitHub Actions; local Docker is not available on the current host.

1. Select the authorized Render workspace and reuse an existing Student-Vault service if one exists. Use Singapore to match the intended Neon region when creating the service.
2. Set secure runtime/build environment variables: `DATABASE_URL` for the explicitly verified **test/demo branch only**, `FRONTEND_URL` equal to the exact HTTPS origin (no `/app` path), `CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `CLERK_WEBHOOK_SECRET`, and `TEACHER_CLERK_IDS` (comma-separated Clerk user IDs). `CLERK_PUBLISHABLE_KEY` is also a Docker build argument consumed as `VITE_CLERK_PUBLISHABLE_KEY`; rebuild after changing it. Other secrets are runtime only. Never paste secrets into chat, command arguments, Git, screenshots or frontend variables.
3. In Clerk configure the exact public origin/domain, sign-in/sign-up redirects to `/app/dashboard` and sign-out to `/app/`. Development-instance domain restrictions may require a supported production instance. Configure webhook endpoint `<public-origin>/api/webhooks/clerk`, subscribe to user.created/user.updated/user.deleted, and put that endpoint's signing secret in Render. Use separate student/teacher synthetic test accounts, not shared public credentials. Account and domain configuration requires the owner.
4. Review migration history and schema before migrating. A schema created before Prisma migrations must be compared with the historical Phase 2 schema before recording the initial baseline. The additive teacher migration is not a substitute for this check.
5. For the specifically confirmed empty test branch, the optional `backend/scripts/prepare-demo-database.mjs` refuses existing migration history or nonempty user/topic/resource tables and compares the live schema with the preserved Phase 2 commit. The owner can place `DEMO_DATABASE_URL` in ignored `backend/.env.demo.local` using their editor. Run from `backend`: `node --env-file=.env.demo.local scripts/prepare-demo-database.mjs --expected-host=<verified-test-endpoint-host>`. This is read-only by default. Only after a passing comparison and owner-reviewed target, rerun with `--apply` to record the verified baseline, deploy pending migrations and compare live schema with the current schema. It never resets or drops tables. Do not use it for populated or unidentified databases. Ordinary deployments with established history use `npm run prisma:migrate:deploy` through the host's secure environment.
6. Verify database branch expiry and retention. The confirmed `student-vault-test` branch expires **2026-11-17 16:00 UTC**. Keep the demo branch available only for the intended test window; arrange owner-approved retention before advertising longer availability. Do not silently switch to production.
7. After a successful build/deploy, run `node scripts/verify-release.mjs <actual-https-origin>` from the repository root. This read-only smoke check covers redirect, compiled JS, deep links, health/readiness, anonymous API denials and private-file protection. It does not prove browser rendering, sign-in or persistence. Browser-test fresh student and teacher sessions, membership/ownership denials, interventions and refresh persistence using synthetic data before marking the release verified.

For the public student preview, also verify the guest path directly from the landing page. Open Attendance, record a present and an absent class, reload, and verify the result and selected route. Create a note on a sample topic and verify that it reopens in the same browser. Test the direct YouTube search link independently of the optional in-app search provider. For hosted study notes, set one supported provider key in Render (`OPENAI_API_KEY` or `ANTHROPIC_API_KEY`), ask a synthetic question in a signed-in student session, and save the answer to a topic. Verify the saved note after reload.

The Render connector cannot by itself configure Clerk's dashboard or complete a human sign-in/MFA flow. A public URL must be reported as partially verified until those steps pass. Do not publish a guessed live link, set the repository homepage, or create a production release tag before actual HTTPS verification.

Use Node 22.12 or newer, Python 3.12 with `backend/requirements-documents.txt`, and PostgreSQL. Run `npm ci`, `npm run prisma:generate`, and `npm run build` in backend; run `npm ci` and `npm run build` in frontend. CI initializes a disposable native PostgreSQL cluster on loopback port 55439 and runs the migration, persistence, and regression checks. It uses the runner's PostgreSQL package, prints its version and server identity, and stops the cluster afterward. Loopback trust authentication is restricted to this disposable CI setup. The workflow requires no real provider or Clerk credentials. Frontend tests run in the test environment; the build runs with `NODE_ENV=production`.

Configure runtime secrets through the host's secret manager: `DATABASE_URL`, `CLERK_SECRET_KEY`, `CLERK_PUBLISHABLE_KEY`, `CLERK_WEBHOOK_SECRET`, and `FRONTEND_URL`. Set `NODE_ENV=production`, `PORT`, and the explicit `TEACHER_CLERK_IDS` allowlist. Optional integrations are documented in the backend README. Never bake `.env` into an image or publish it with frontend files.

Before release, take a database snapshot, inspect migration history with `npx prisma migrate status`, and apply reviewed migrations with `npm run prisma:migrate:deploy`. An existing database without migration history must be verified against the initial schema before baselining. Do not run `migrate reset` or `db push` on a deployment database.

Serve `frontend/dist` at `/app/` with SPA fallback to `/app/index.html`. Forward `/api/` to the backend started with `npm start`. Terminate TLS at a reverse proxy and restrict direct access to the backend. Configure Clerk's allowed origins/redirects and webhook URL for that hostname. Keep the exact frontend origin in `FRONTEND_URL`.

Use `/api/health` for process liveness. Use `/api/ready` for database connectivity readiness: it returns 200 with `status: ready` when `SELECT 1` succeeds and 503 with `status: unavailable` on failure or a two-second response timeout. It exposes no database details and requires no Clerk token. Results are cached internally for two seconds, and concurrent probes share one outstanding query; the HTTP timeout does not cancel that query. Configure PostgreSQL/client connection and query timeouts as well. Readiness proves connectivity, not migration state or external provider availability; migration checks remain a release step. Monitor HTTP 5xx rate, response latency, process restarts, and database connectivity using the hosting platform; alert on sustained failures. Logs must exclude authorization headers, student documents, and provider payloads. Process shutdown closes Fastify and disconnects Prisma.

Rate limits are per process. Deploy a single backend instance until a shared gateway limit is configured; horizontal scaling without a shared limit increases the effective allowance. Apply ingress upload limits consistent with the API's endpoint limits. Enable managed PostgreSQL backups and point-in-time recovery where supported.

Rehearse restore in a separate isolated database: restore a provider snapshot or a `pg_dump --format=custom` backup with `pg_restore --no-owner` into a newly created empty database. Verify migration status, schema consistency, row counts, and the authorization/intervention workflows before considering the restore usable. Never restore over the live database as a test. Retain encrypted backups under access controls, with retention decided by the data owner.

Rollback application releases to a previously built artifact only if compatible with the migrated schema. Prefer a reviewed forward migration for schema corrections. A destructive rollback requires a maintenance window and a verified restore plan.

Release verification still requires a real Clerk test account for student/teacher sign-in and browser flows, explicitly opted-in synthetic documents for live OCR/AI checks, and deployment access for TLS, proxy, backup/restore, and monitoring checks. Local tests do not establish these external properties.
